Harbor Staking: 48h pre-audit report

This is the format you get from a $499 pre-audit. The project, code and findings are made up to show the format. The bugs are real bug classes that we see in staking contracts.

Report ID · SNTX-PA-SAMPLE-01 Commit · a3f9c1e Scope · HarborStaking.sol, 212 nSLOC Window · 48 hours

1. Summary

HarborStaking lets users stake HBR and earn rUSD at a fixed rate per second, split pro rata by stake. We found one High, which lets a new staker take rewards that were earned by existing stakers. We also found one Medium, two Low and two informational issues. The High is proven with a Foundry test, included below.

2. Scope and method

  • In scope: src/HarborStaking.sol at commit a3f9c1e (212 nSLOC). Tokens are standard OpenZeppelin ERC-20s. The owner is a 2-of-3 multisig.
  • Out of scope: token contracts, deployment scripts, frontend and off-chain keepers.
  • Method: two manual passes (one for access control and state, one for reward math), Slither and Aderyn with every result triaged, and a Foundry test for each High or Critical candidate. Anything we couldn't prove with a test was downgraded or dropped.
  • Severity: impact × likelihood, using our published scale.

3. Findings

High  H-01 · stake() does not settle rewards, so a new staker takes rewards earned by others

Location: HarborStaking.sol#L58-L63

withdraw() and claim() use the updateReward modifier, but stake() does not. This causes two problems:

  1. totalStaked goes up before rewardPerTokenStored is updated. All the time since the last update is then shared over the new, larger total, and the newcomer gets part of rewards that were earned before they arrived.
  2. A first-time staker's userRewardPerTokenPaid stays at 0. Their first claim therefore pays them as if they had staked since the contract began.
function stake(uint256 amount) external {            // no updateReward(msg.sender)    stakeToken.transferFrom(msg.sender, address(this), amount);    balanceOf[msg.sender] += amount;    totalStaked += amount;}

Impact: anyone can stake right before a claim and walk away with a share of rewards that belong to existing stakers. In our test, Bob stakes for 0 seconds and receives half of 30 days of emissions. Alice loses the same amount.

Proof of concept (passes on commit a3f9c1e, fails after the fix):

function test_H01_lateStakerTakesAccruedRewards() public {    vm.prank(alice); staking.stake(100e18);          // t0: Alice is the only staker    vm.warp(block.timestamp + 30 days);              // 30 days of rewards are Alice's    vm.prank(bob); staking.stake(100e18);            // no settlement before totalStaked doubles    vm.prank(bob); staking.claim();                  // same block    uint256 accrued = 30 days * RATE;    assertApproxEqRel(rewardToken.balanceOf(bob), accrued / 2, 1e15); // Bob gets 50%    assertApproxEqRel(staking.earned(alice),        accrued / 2, 1e15); // Alice lost 50%}

Fix: add updateReward(msg.sender) to stake(). Also add a test asserting that someone who stakes and claims in the same block receives 0.

function stake(uint256 amount) external updateReward(msg.sender) {    stakeToken.safeTransferFrom(msg.sender, address(this), amount);    balanceOf[msg.sender] += amount;    totalStaked += amount;}

Medium  M-01 · setRewardRate() applies the new rate to time that has already passed, and is not checked against funding

Location: HarborStaking.sol#L91-L94

setRewardRate() writes rewardRate without settling rewardPerTokenStored first. The new rate is then applied back to lastUpdate. If the rate goes down, stakers lose rewards they had already earned. If it goes up, they are paid for time that was never funded. The function also doesn't check that the contract holds enough rUSD to pay rate × remaining duration, so the last people to claim can find the contract empty.

Likelihood: only the owner can call this, and the owner is trusted, so this is Medium rather than High. It still happens without any bad intent on a normal rate change.

Fix: add updateReward(address(0)) to the function, and require rewardToken.balanceOf(address(this)) - owed >= newRate * (periodFinish - block.timestamp).

Low  L-01 · Unchecked ERC-20 return values

transfer and transferFrom are called without checking what they return. This is safe for the current tokens, but becomes a silent failure if either token is ever replaced by one that returns false. Fix: use OpenZeppelin SafeERC20.

Low  L-02 · No zero-address checks in the constructor

The token addresses are immutable. A zero address passed at deploy time means redeploying and migrating. Fix: require(_stake != address(0) && _reward != address(0)). Team response: the deploy script checks this. Acknowledged.

Info  I-01 · Floating pragma

pragma solidity ^0.8.0;: pin the compiler version you tested with (for example 0.8.24).

Info  I-02 · No events on state changes

Without events, monitoring and indexers can't track stakes, claims or rate changes. Emit Staked, Withdrawn, RewardPaid and RewardRateUpdated.

4. What we checked and ruled out

  • Reentrancy: state is updated before the external calls in withdraw() and claim(), and both tokens are plain ERC-20s with no hooks. Not exploitable.
  • Rounding: reward math is scaled by 1e18. The rounding loss is <1 wei per user per update, so it can't be farmed.
  • Division by zero: rewardPerToken() returns the stored value when totalStaked == 0. Safe.
  • Access control: setRewardRate and recoverERC20 are onlyOwner. recoverERC20 blocks the stake token, so the owner can't take user deposits.

5. Fix verification

Fix commit 7be20d4 reviewed: H-01, M-01, L-01, I-01 and I-02 are resolved. The H-01 test now fails as expected (Bob receives 0), and the team added it to their suite as a regression test. L-02 is acknowledged.

6. Limits of this review

This was a 48-hour, time-boxed review of one commit and the files listed above. It reduces risk but doesn't guarantee there are no bugs. Contracts that will hold significant value should also get a full audit, invariant tests and a bug bounty.
